# 第二章 操作系统结构

## 2.1 操作系统的机制与策略
- 设计原则：策略与机制分离
  - 策略（Policy）：做什么，相对动态
  - 机制（Mechanism）：怎么做，相对静态
- 好处
  - 调整策略适应不同应用需求
  - 优化机制完善对策略的支持

---

## 2.2 操作系统复杂性的管理方法——M.A.L.H方法
- **模块化（Modularity）**
  - 分治法：分解为通过明确接口交互的模块
  - 高内聚、低耦合
- **抽象（Abstraction）**
  - 接口与实现分离
  - 减少模块间交互，减少错误传播
- **分层（Layering）**
  - 模块化 + 抽象，强调层内完整性
  - 约束：只能与同层及相邻上下层交互，不跨层
  - 不同类模块间的层次化
- **层级（Hierarchy）**
  - 强调包含关系
  - 功能相近的模块组成自包含子系统
  - 同类模块间的分层

## 2.3 操作系统内核架构

### 2.3.1 简要结构
- 应用与操作系统在同一地址空间
- 无内存管理、无特权级隔离
- 适用于微控制单元等简单硬件
- 优点：快
- 缺点：无隔离，单点崩溃影响整体
- 典型：MS-DOS

### 2.3.2 宏内核
- 分层：内核层（特权级）+ 应用层（非特权级）
- 内核整合：文件系统、内存管理、设备驱动、进程调度、同步原语、IPC
- 典型：Linux
- 优点
  - 丰富社区生态，经30年优化
- 结构性缺陷
  - 安全与可靠性：模块间无强隔离，故障易扩散
  - 实时性：系统复杂，无法最坏情况时延分析
  - 庞大阻碍创新：Linux代码超2000万行
- 难满足场景
  - 向上/向下扩展（KB级到TB级）
  - 硬件异构性
  - 功能安全（无法通过ASIL-D）
  - 信息安全（单点崩溃，大量CVE）
  - 确定性时延

### 2.3.3 微内核
- 设计原则：最小化内核功能
- 操作系统功能移至用户态（服务/Server）
- 用户模块间通过消息传递（IPC）通信
- 发展
  - 第一代：Mach（1985），IPC通用但资源占用大
  - 第二代：L3/L4，最小化原则，性能极高，可能DoS
  - 第三代：seL4，Capability机制 + 形式化证明
- 优点
  - 易扩展、易移植、更可靠、更安全（进程粒度隔离）、更健壮
- 缺点
  - 性能较差（函数调用 → IPC）
  - 生态欠缺
  - 重用宏内核兼容性带来新问题

### 2.3.4 混合内核
- 宏内核 + 微内核结合：性能模块放回内核态
- 典型
  - macOS/iOS：Mach微内核 + BSD 4.3 + 系统框架
  - Windows NT：微内核 + 内核态系统服务 + 系统框架

### 2.3.5 外核
- Exokernel + LibOS
- Exokernel不提供硬件抽象，不管理资源，只管理应用，负责资源绑定与回收，保证隔离
- Exokernel把时间切片，单切片内只服务一个应用
- 库OS（LibOS）
  - 策略与机制分离，硬件抽象以库形式提供
  - 高度定制化，不同应用可用不同LibOS
  - 更高性能（函数调用直接交互）
  - 更安全可靠（内核极小，LibOS强隔离）
- 设计原则：“管理与保护分离”
- Exokernel功能：追踪资源拥有权、保证资源保护、回收资源访问权
- 对应技术
  - 安全绑定：LibOS与资源绑定（可用性 + 隔离性）
  - 显式回收：Exokernel告知资源分配，应用租期结束前主动归还
  - 终止协议：应用不归还则强制中止
- 优点
  - OS无抽象，理论最优性能
  - 应用精确实时控制
  - LibOS用户态易调试
- 缺点
  - 资源利用效率由应用决定
  - 定制化多，维护难度增加
  - 可能无法识别运行的操作系统类型

### 2.3.6 多内核
- 实验型架构，众核系统视为多核通过网络互联的分布式系统
- 节点间通过进程间通信交互
- 设计思路
  - 每核运行独立小内核（OS node）
  - 应用运行在OS node之上
  - 节点间高速互连通信
- 优点
  - 避免隐式共享带来的性能可扩展性瓶颈
  - 易支持异构处理器
- 缺点
  - 节点间状态冗余，资源开销
  - 应用需使用多内核线程间通信接口，需移植
  - 绝对性能不一定有优势
- 典型案例
  - Barrelfish（ETH/Zurich）：Dispatcher + Domain，支持CPU/ARM/GPU
  - Popsicle Linux：多ARM核异构，各核独立内核实例，上层统一接口

### 2.3.7 操作系统架构及演进
- 尽可能集成现有POSIX API/Linux ABI
- 避免棘手的系统调用（如fork）
- 避免不可扩展的POSIX API

## 2.4 操作系统框架结构（Android）

### 分层架构设计
- **Linux内核层**：硬件驱动、进程管理、内存管理
- **硬件抽象层（HAL）**
  - 封装硬件实现细节，解耦内核与上层框架
  - 规避GPL协议（厂商可不开源核心驱动）
- **Android系统框架层**
  - Android库（自定义库 + 重写标准库）
  - Android运行时（ART/Dalvik）
    - Dalvik（旧）：JIT编译
    - ART（新，Android 5.0+）：AOT预编译，Java字节码预转机器码
- **应用框架层**：Activity Manager、Window Manager、Service Manager等

### 服务化架构与Binder IPC
- 体现微内核设计思想
- 解耦：组件服务化，App通过Binder IPC发起请求
- 交互流程
  1. 服务注册：系统服务在Service Manager注册
  2. 服务发现：App通过Service Manager查找服务句柄
  3. 服务请求：App通过Binder IPC发送请求并获取响应
- 优势：可扩展性、可维护性，单服务崩溃不影响整体内核

### Dalvik vs ART
| 特性     | Dalvik（旧）          | ART（新）                |
| -------- | --------------------- | ------------------------ |
| 编译时机 | JIT（运行时即时编译） | AOT（安装时预编译）      |
| 运行速度 | 较慢，运行时开销      | 较快，直接执行二进制代码 |
| 系统能耗 | 较高（编译消耗CPU）   | 较低（减少重复编译）     |
